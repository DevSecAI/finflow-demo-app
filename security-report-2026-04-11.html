Application Summary

A financial transaction management application with user authentication, transaction history tracking, and administrative query capabilities. Built with Express backend and React frontend, using SQLite for data persistence and JWT for authentication.

Technology Stack

Express.jsReactSQLiteJWTDockerAWS SDKStripeTerraform

Data Flows

  • User input enters via REST API endpoints (/register, /login, /transfer, /query, /export)
  • Authentication via JWT tokens passed in request headers
  • Data processed through Express route handlers with minimal validation
  • Data stored in SQLite database with direct SQL query concatenation
  • Data retrieved and returned in JSON responses to frontend
  • Administrative exports via shell command execution with user-supplied parameters

Attack Surface

  • POST /register - User registration with no email validation or rate limiting
  • POST /login - Authentication endpoint vulnerable to SQL injection
  • POST /reset-password - Predictable token generation and indefinite validity
  • POST /transfer - Transaction creation with IDOR and SQL injection vulnerabilities
  • PUT /update/:id - Transaction modification without ownership verification
  • GET /history/:userId - Transaction history accessible to any authenticated user
  • POST /query - Arbitrary SQL execution endpoint for admins
  • POST /export - Shell command injection via filename/format parameters
  • GET /user/:id - User data retrieval without authorization checks
  • POST /api/calculate - Unauthenticated endpoint with eval() on user input
  • File upload handlers (2 detected) - No validation details provided
  • JWT token handling - 30-day expiry, full user object in responses

Vulnerability Details

CRITICAL Arbitrary Code Execution via eval() on User Input
backend/server.js:59

The /api/calculate endpoint uses eval() directly on user-supplied formula input without any validation, sanitization, or authentication. This allows unauthenticated attackers to execute arbitrary JavaScript code on the server.

Recommendation: Remove eval() entirely, use a safe math expression parser, add authentication
CRITICAL JWT Signature Verification Bypass via jwt.decode()
backend/routes/admin.js:13

The adminOnly middleware uses jwt.decode() instead of jwt.verify(). The decode() function does NOT verify the JWT signature, allowing attackers to forge arbitrary tokens with admin role claims.

Recommendation: Replace jwt.decode() with jwt.verify() using proper secret
CRITICAL Arbitrary SQL Execution via /query Endpoint
backend/routes/admin.js:42

The /query endpoint accepts raw SQL from request body and executes it directly without any validation or parameterization. Combined with the forged JWT vulnerability, this allows complete database compromise.

Recommendation: Remove this endpoint entirely - never allow arbitrary SQL execution
CRITICAL Shell Command Injection in /export Endpoint
backend/routes/admin.js:25

User-supplied filename and format parameters are directly concatenated into a shell command executed via exec(). An attacker can inject shell metacharacters to execute arbitrary commands on the server.

Recommendation: Validate and sanitize filename/format, use safe file operations instead of shell commands
CRITICAL SQL Injection in Transaction Update Endpoint via Mass Assignment

HIGH IDOR: No Ownership Verification in Transaction Update

Recommendation: 1. Add ownership verification: JOIN with users table to verify req.user.id owns the transaction 2. Implement field whitelisting instead of mass assignment 3. Fix authentication middleware to properly validate JWT signatures
HIGH IDOR: No Ownership Verification in Transaction History
backend/routes/transactions.js:23

The /history/:userId endpoint allows any user (including unauthenticated guests) to view transaction history of any other user by manipulating the userId parameter in the URL. The looseyAuth middleware fails open and uses jwt.decode() instead of jwt.verify(), meaning tokens are not cryptographically validated.

Recommendation: 1. Fix looseyAuth to use jwt.verify() with proper signature validation 2. Add ownership check: WHERE (from_user = ${userId} OR to_user = ${userId}) AND (from_user = ${req.user.id} OR to_user = ${req.user.id}) 3. Reject requests without valid authentication
HIGH IDOR - Unrestricted Access to User Transaction History
backend/routes/transactions.js:23

The /history/:userId endpoint accepts userId from URL parameter without verifying the requesting user owns that account. Combined with broken JWT verification in looseyAuth middleware, any user can access any other user's transaction history.

Recommendation: 1. Fix looseyAuth to use jwt.verify() with proper secret validation 2. Add authorization check: if (req.user.id !== parseInt(userId)) return 403 3. Consider removing userId from URL and using authenticated user's ID instead
